GitHub Delivery Operating System

Structured sprint execution, QA governance, and production release control — embedded in your GitHub repos. Start with the small set or the full system, change it any time, and run it all by asking Claude Code in plain language.

New in 1.13: a lite install for one person or a small project, the ability to add or remove pieces whenever your needs change (just ask Claude), and a setup assistant that helps you choose. Telegram alerts are now opt-in.

Start small or take everything

Delivery OS comes in two sizes. Pick the one that fits today. Nothing is locked in: you can add or remove pieces whenever your needs change, just by asking Claude.

Start with lite → Start with full → Not sure? Let Claude guide you →

Shipping a release with lite: open a Production Release issue and it pings the release approver. They comment approved and it gets ready-for-deploy; declined holds it back, and approving again lifts that. There is no QA approver to set up. The install sets RELEASE_APPROVER to you (it never overwrites a value that's already set, and --no-set-approvers turns it off).

Get started

Open Claude Code in the repo you want to set up and paste one of these prompts. Claude previews the install first and only writes files after you confirm.

Not sure? Let Claude guide you

Claude asks a few plain questions (just you or a team? does anyone test before release?), recommends lite, full or a hand-picked set, shows a preview, and installs after you say yes. It also adds the repo's delivery-ops skill, so from then on you only ever talk to Claude.

Show me a dry run ("npx github-delivery-os install ... --dry-run .") and only install after I say yes. Include the Claude Code skill.

Want a permanent setup assistant instead? Run this once in a terminal. The setup skill then works in any repo, including ones with no Delivery OS yet, and you just say "Set up Delivery OS here."

Install lite

For one person or a small project: sprints, task and bug forms, and a release that one approval ships. The install makes you the release approver (it sets RELEASE_APPROVER to your GitHub login via gh, never overwrites an existing value, and Claude tells you first).

Paste into Claude Code, from your repo root
Install the lite version of GitHub Delivery OS in this repo with the Claude Code skill: run "npx github-delivery-os install --bundle lite --with-templates --with-labels --with-skill --dry-run ." first and show me what it would change. If that looks right, run it without --dry-run, then run "npx github-delivery-os status ." to confirm. Labels need gh auth, so tell me if that's missing.

Install the full system

For a team with a QA step: the rolling QA issue, QA approval, QA assignment, and releases that need a QA approver too.

Change it any time

Once Delivery OS is installed with the delivery-ops skill, just ask Claude. It previews with a dry run, explains the consequence in plain words, and waits for your yes before changing anything.

Say this What happens
"What do I have installed?"Every workflow shown as installed or not, and each pack's state.
"Add QA sign-off."Adds the rolling QA issue, QA approval, QA assignment, the QA Request form and QA labels, and a release then needs a QA approver too. You set QA_APPROVER and QA_ASSIGNEES.
"Turn on Telegram alerts."Adds the Telegram workflow. You add the two secrets, TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID.
"Take QA sign-off out." / "Remove auto-assign QA."Deletes only the files nothing else needs. Taking the QA pack out puts a lite repo's one-approver release back.

Behind those phrases, a name can be a pack (a named group) or any single workflow, on a lite or a full install:

Pack What it adds Afterwards
qaThe rolling QA issue, QA approval, QA assignment, the QA Request form and QA labels — and a release that needs a QA approver tooSet QA_APPROVER and QA_ASSIGNEES
telegramTelegram alerts for bugs, QA, sprints, releases and merges. (The Sprint Completed alert is sent by auto-close-sprint itself once the two secrets exist.)Add the secrets TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID
  • A workflow's scripts, the QA form and the QA labels travel with it, and go only when nothing else installed needs them. Your repo variables, secrets and labels already created are never touched.
  • Releases need a QA approver only with the qa pack (or on a full install). Adding a single QA workflow doesn't change how releases work.
  • Removing something another workflow works with (for example sprint-child-creator, which auto-close-sprint counts) prints a note and still does what you asked.
  • Switching a full install to lite doesn't delete anything. The install and status list the QA workflows still on disk, and asking Claude to "take QA sign-off out" (or remove qa) clears them with their scripts and form.
  • A plain install --update keeps your bundle, packs and any workflows you added or removed; status checks exactly what you have.

Delivery Ops: run it by asking Claude

Two Claude Code skills work as one assistant. The setup skill is the front door, used once: it helps you choose what to install and installs it. The delivery-ops skill, which the install puts in your repo, handles everything after: sprints, bugs, releases, approvals, status, and changing what's installed. You never choose between them. Ask in plain words and Claude picks the right one.

Installing with --with-skill (recommended) drops a .claude/skills/delivery-ops/SKILL.md skill into the repo, scoped to that repo's Delivery OS install. It lets anyone using Claude Code drive the workflows above by asking in plain language, instead of hand-building gh issue create calls and remembering each template's exact field names.

Before doing anything, it checks the target repo — confirms Delivery OS is installed, labels exist, and approvers/QA assignees are configured — and always shows the exact issue or comment content for confirmation before creating or posting for real. It can also run a task's whole lifecycle on its own (notice, classify, file, keep in sync, close) — acting without asking when the outcome is clear and always posting a one-line notice so nothing happens invisibly — or turn a spec/feature description into a full phase-and-task breakdown, always shown for confirmation first since that creates many issues at once.

Example: filing a bug and a task, step by step

Illustrative walkthrough against acme/storefront, a repo with Delivery OS installed (same example repo as the full walkthrough below).

Filing the bug:

  1. In Claude Code, inside (or pointed at, via --repo) the target repo, describe the bug in plain language:
    "File a bug on acme/storefront — the order request form submits with an empty phone number, severity high. Steps: fill in the form, leave phone blank, submit. Expected: should block submission. Actual: submits anyway, so there's no way to contact the customer. Tested on Chrome, desktop, production."
  2. Claude pre-flights the repo — confirms Delivery OS is installed and the bug/qa labels exist.
  3. Claude shows the exact issue it's about to create before doing anything: Title [BUG] Order request form submits with empty phone number; Labels bug, qa; body fields (Platform, Severity: High, Build/Version, Steps to Reproduce, Expected/Actual Result, Test Environment) filled in from what you said.
  4. Confirm ("yes") when asked to create it.
  5. Claude runs gh issue create and reports back the issue — e.g. acme/storefront#42. Nothing else happens automatically; bug reports don't trigger a workflow, they're just labeled and tracked.

Filing the follow-up task:

  1. Ask Claude to turn the bug into tracked work, referencing the bug's issue number:
    "Create a task to add phone number validation to the order form, owner @alex, priority P1, status Backlog, acceptance: form blocks submission until a valid phone number is entered. Link it to #42."
  2. Claude shows the constructed issue: Title TASK - Add phone number validation to order form; Labels task; body: Task Summary, Description (references #42), Owner → @alex, Priority → P1 - High, Status → Backlog, Acceptance Criteria, Artifacts/Links → Related bug: #42.
  3. Confirm ("yes") to create it.
  4. Claude runs gh issue create. Same as the bug — no workflow trigger, just labeled and tracked, now linked back to the bug it addresses.

Updating an existing install

Ask Claude:

Paste into Claude Code, from your repo root
Check whether the Delivery OS install in this repo is up to date. If it isn't, show me what an update would change before running it.

An update keeps your choices: your bundle, any packs, and any workflows you added or removed. A repo that already had the Telegram alerts keeps them, and they keep updating. A default install no longer includes them (add with "Turn on Telegram alerts").

You don't have to remember to check. A repo installed with the skill also gets an update check: when a Claude Code session starts there and the install is behind, Claude offers to run the update (only after you confirm). Prefer the terminal? See the command reference.

Why this exists

Engineering teams often rely on informal coordination in GitHub — manual approvals, inconsistent sprint tracking, reactive QA, and socially enforced releases. As teams scale, that creates:

  • Delivery ambiguity
  • QA bottlenecks
  • Unclear accountability
  • Release risk
  • Cross-team misalignment

Delivery OS embeds structured intake, sprint orchestration, QA governance, and release gates directly into your repos — without replacing CI/CD or disrupting workflows.

What you get

Sprint child creation Create a sprint issue → each feature line becomes a child issue. Burn-down and auto-close at 100%.
Dual approval gates Full: production releases require both release approver and QA sign-off before deploy. A decline from either side blocks it until that same person approves. Lite: one approver ships it.
Start small, grow later A lite install for one person or a small project. Ask Claude to add or remove any pack or workflow whenever your needs change.
Auto-assign QA Issues with qa or qa-request labels get assigned to your QA team.
Telegram alerts Optional notifications for bugs, QA requests, sprints, and releases. Opt-in: ask Claude to turn them on.
One assistant for Claude Code A setup skill helps you choose and install; the delivery-ops skill (--with-skill) then runs everything: issues, approvals, status, task tracking, and changing what's installed — in plain language.

Workflows

Lite installs the five marked Lite, with simpler single-approver versions of notify-release-approver and authorize-deployment. Packs add the rest.

Workflow Trigger Purpose
sprint-child-creator
Lite + Full		Issue opened, title contains SPRINT -Parses "Sprint Features (One Per Line)" and creates one child issue per line, each linked back with Parent Sprint: #N
auto-close-sprint
Lite + Full		Issue closed or reopened, body contains Parent SprintRecomputes the parent sprint's burn-down/health and rewrites its status section; auto-closes the sprint at 100%. Tasks closed as not planned leave the count, and reopening a task updates the burn-down and reopens a sprint that had closed itself. Also sends the Sprint Completed Telegram alert itself when the two Telegram secrets exist.
notify-release-approver
Lite + Full		Issue opened, labeled productionComments on the issue tagging the repo's RELEASE_APPROVER, and posts a What's in this release roll-up of the plain-English changelogs from QA Requests since the last authorized release (informational; refresh via workflow_dispatch)
authorize-deployment
Lite + Full		Comment posted on a production-labeled issueChecks the commenter and keyword against RELEASE_APPROVER/QA_APPROVER (each may be a comma-separated list). Once both sides approve, adds ready-for-deploy; a decline from any release or QA approver adds declined and stands until that same person approves. On approval it also closes the Tasks/QA Requests auto-qa-request filed for work in the release (opt out: DELIVERY_OS_AUTO_CLOSE=false)
auto-assign-qa
Full · pack: qa		Issue opened/labeled qa or qa-requestAssigns the repo's configured QA_ASSIGNEES
telegram-issues
Opt-in · pack: telegram		Issue/comment/PR eventsNot in a default install; ask Claude to turn on Telegram alerts (or run npx github-delivery-os add telegram .). Sends a Telegram alert if TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID are configured
auto-qa-request
Full · pack: qa		Push to main, including PR merges (plus PR events in per-change mode)QA reminder for every change that isn't docs/settings-only or [skip qa-request]. Default: adds a line (with a plain-English draft and any linked #N) to the one open rolling QA issue, opening it if needed. DELIVERY_OS_AUTO_QA_MODE=per-change files a QA Request (+ Task) per change instead; off files nothing
qa-rollup-approval
Full · pack: qa		Comment on, or edit of, the rolling QA issueThe QA_APPROVER approves (a comment starting with e.g. approved, lgtm, ✅, or ticking the Approved box), which closes it, or declines (needs work, not ok, ❌), which keeps it open. With several QA approvers, a decline stands until that same person approves. Anyone else is ignored with a reply
setup-labels
Lite + Full		Manual (workflow_dispatch)One-time run that creates all labels Delivery OS needs

Quick start (after install)

  1. Create labels: Actions → Setup Labels → Run workflow
  2. Configure variables: Settings → Secrets and variables → Actions → Variables
    Full: RELEASE_APPROVER, QA_APPROVER, QA_ASSIGNEES. Lite: just RELEASE_APPROVER, which the install sets to you.
  3. Optional: QA reminders default to one rolling QA issue — switch with DELIVERY_OS_AUTO_QA_MODE (rolling/per-change/off), and tune with DELIVERY_OS_AUTO_QA_QUIET_PATHS, DELIVERY_OS_AUTO_TASK and DELIVERY_OS_AUTO_CLOSE (see consumer setup)
  4. Optional: for Telegram alerts, ask Claude to "turn on Telegram alerts", then add TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID as repo secrets

Command reference

Everything above is also available as plain commands, for people who prefer the terminal or want to script it.

Show every command

Install from a terminal

No clone, no config. From your repo root, just run:

From your repo root
npx github-delivery-os install --with-templates --with-labels --with-skill .

Add --with-labels to create labels via gh CLI (requires gh auth). Add --with-skill to also drop in a Claude Code skill for operating the installed repo — creating sprint/release/QA/bug issues, commenting as an approver, checking status, autonomous task tracking (identify, file, update, and close issues as work progresses), and turning a spec or feature description into a full phase-and-task breakdown — without knowing the underlying gh commands. Use --dry-run to preview first.

Command When to run it
install --with-templates .First install — workflows + issue templates
install --with-templates --with-labels .Also create labels immediately via gh CLI
install --with-templates --with-skill .You'll operate this repo's Delivery OS from Claude Code
install --with-templates --with-labels --with-skill .Everything at once, in one command
install --bundle lite --with-templates --with-labels --with-skill .One person or a small project — sprints, tasks, bugs and a single-approver release, without the QA machinery. Sets you as the release approver
install --only a,b … / --skip a,bPick individual workflows (names from list) instead of a whole bundle
list .See every bundle, pack and workflow, and which are installed in this repo (--json for tools)
add qa . / add telegram . / add <workflow> .Add a pack or a single workflow later, without reinstalling (--dry-run to preview)
remove qa . / remove <workflow> .Take a pack or workflow away again; deletes only the files nothing else needs
setup-skillAdd the Claude Code skill that helps you choose what to install, before anything is installed
install --dry-run …Preview any combination above — nothing is written
install --update …Update an existing install, or add a flag you skipped earlier
status .Check what's installed, its version, and for broken installs
shell-hook --installGet a reminder in your terminal when you cd into an out-of-date repo
uninstall --with-templates --with-skill .Remove everything, including templates and the skill

Check and update from a terminal

Check what's installed and whether a newer version is available:

Check status
npx github-delivery-os@latest status .

Then pull the latest workflows, templates, labels, and skill. --update replaces files that are already installed; without it, existing files are skipped:

Update to latest
npx github-delivery-os@latest install --with-templates --with-labels --with-skill --update .

For a reminder in any terminal whenever you cd into an out-of-date repo:

Terminal reminder (zsh or bash)
npx github-delivery-os@latest shell-hook --install
