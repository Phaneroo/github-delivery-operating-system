GitHub Delivery Operating System

Structured sprint execution, QA governance, and production release control — embedded directly in your GitHub repos.

One command to install

Add Delivery OS to any repository. No clone, no config — just run:

From your repo root
npx github-delivery-os install --with-templates --with-labels --with-skill .

Add --with-labels to create labels via gh CLI (requires gh auth). Add --with-skill to also drop in a Claude Code skill for operating the installed repo — creating sprint/release/QA/bug issues, commenting as an approver, checking status, autonomous task tracking (identify, file, update, and close issues as work progresses), and turning a spec or feature description into a full phase-and-task breakdown — without knowing the underlying gh commands. Use --dry-run to preview first.

Command When to run it
install --with-templates .First install — workflows + issue templates
install --with-templates --with-labels .Also create labels immediately via gh CLI
install --with-templates --with-skill .You'll operate this repo's Delivery OS from Claude Code
install --with-templates --with-labels --with-skill .Everything at once, in one command
install --dry-run …Preview any combination above — nothing is written
install --update …Update an existing install, or add a flag you skipped earlier
status .Check what's installed, its version, and for broken installs
uninstall --with-templates --with-skill .Remove everything, including templates and the skill

Updating an existing install

Check what's installed and whether a newer version is available:

Check status
npx github-delivery-os@latest status .

Then pull the latest workflows, templates, labels, and skill. --update replaces files that are already installed; without it, existing files are skipped:

Update to latest
npx github-delivery-os@latest install --with-templates --with-labels --with-skill --update .

Why this exists

Engineering teams often rely on informal coordination in GitHub — manual approvals, inconsistent sprint tracking, reactive QA, and socially enforced releases. As teams scale, that creates:

  • Delivery ambiguity
  • QA bottlenecks
  • Unclear accountability
  • Release risk
  • Cross-team misalignment

Delivery OS embeds structured intake, sprint orchestration, QA governance, and release gates directly into your repos — without replacing CI/CD or disrupting workflows.

What you get

Sprint child creation Create a sprint issue → each feature line becomes a child issue. Burn-down and auto-close at 100%.
Dual approval gates Production releases require both release approver and QA sign-off before deploy.
Auto-assign QA Issues with qa or qa-request labels get assigned to your QA team.
Telegram alerts Optional notifications for bugs, QA requests, sprints, and releases.
Claude Code skill Optional (--with-skill): operate the installed repo from Claude Code — create issues, comment as an approver, check status, track tasks autonomously — in plain language.

Workflows installed

Workflow Trigger Purpose
sprint-child-creatorIssue opened, title contains SPRINT -Parses "Sprint Features (One Per Line)" and creates one child issue per line, each linked back with Parent Sprint: #N
auto-close-sprintIssue closed, body contains Parent SprintRecomputes the parent sprint's burn-down/health and rewrites its status section; auto-closes the sprint at 100%
notify-release-approverIssue opened, labeled productionComments on the issue tagging the repo's RELEASE_APPROVER, and posts a What's in this release roll-up of the plain-English changelogs from QA Requests since the last authorized release (informational; refresh via workflow_dispatch)
authorize-deploymentComment posted on a production-labeled issueChecks the commenter and keyword against RELEASE_APPROVER/QA_APPROVER; once both approve, adds ready-for-deploy and closes the Tasks/QA Requests auto-qa-request filed for work in the release (opt out: DELIVERY_OS_AUTO_CLOSE=false)
auto-assign-qaIssue opened/labeled qa or qa-requestAssigns the repo's configured QA_ASSIGNEES
telegram-issuesIssue/comment/PR eventsSends a Telegram alert if TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID are configured
auto-qa-requestPush to main; PR merged (and opened/updated/closed in per-change mode)QA reminder for every change that isn't docs/settings-only or [skip qa-request]. Default: adds a line (with a plain-English draft and any linked #N) to the one open rolling QA issue, opening it if needed. DELIVERY_OS_AUTO_QA_MODE=per-change files a QA Request (+ Task) per change instead; off files nothing
qa-rollup-approvalComment on, or edit of, the rolling QA issueThe QA_APPROVER approves (a comment starting with e.g. approved, lgtm, ✅, or ticking the Approved box), which closes it, or declines (needs work, not ok, ❌), which keeps it open. Anyone else is ignored with a reply
setup-labelsManual (workflow_dispatch)One-time run that creates all labels Delivery OS needs

Quick start (after install)

  1. Create labels: Actions → Setup Labels → Run workflow
  2. Configure variables: Settings → Secrets and variables → Actions → Variables
    RELEASE_APPROVER, QA_APPROVER, QA_ASSIGNEES
  3. Optional: QA reminders default to one rolling QA issue — switch with DELIVERY_OS_AUTO_QA_MODE (rolling/per-change/off), and tune with DELIVERY_OS_AUTO_QA_QUIET_PATHS, DELIVERY_OS_AUTO_TASK and DELIVERY_OS_AUTO_CLOSE (see consumer setup)
  4. Optional: Add TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID for alerts

Operating from Claude Code

Installing with --with-skill drops a .claude/skills/delivery-ops/SKILL.md skill into the repo, scoped to that repo's Delivery OS install. It lets anyone using Claude Code drive the workflows above by asking in plain language, instead of hand-building gh issue create calls and remembering each template's exact field names.

Before doing anything, it checks the target repo — confirms Delivery OS is installed, labels exist, and approvers/QA assignees are configured — and always shows the exact issue or comment content for confirmation before creating or posting for real. It can also run a task's whole lifecycle on its own (notice, classify, file, keep in sync, close) — acting without asking when the outcome is clear and always posting a one-line notice so nothing happens invisibly — or turn a spec/feature description into a full phase-and-task breakdown, always shown for confirmation first since that creates many issues at once.

Ask ClaudeWhat happens
"Create a sprint called Sprint 14 for <goal>, running <start> to <end>, with features: …"Opens a Sprint Planning issue; sprint-child-creator splits each feature into its own child issue
"Open a production release for <project> v2.4.1, sprint #N, summary: …"Opens a release issue; notify-release-approver tags the configured approver
"Approve release #N" / "Decline release #N — <reason>"Verifies the authenticated login matches RELEASE_APPROVER, then posts a comment with the right keyword
"Open a QA request for <feature>, related to #N, testing …"Opens a QA request; auto-assign-qa assigns the configured team
"Mark QA #N as approved"Same login check against QA_APPROVER, then posts the right keyword
"File a bug: <summary>, severity <level>, steps: …"Opens a bug report with platform, severity, steps, expected/actual result
"Create a task to <summary>, owner <name>, priority P1"Opens a Task issue — plain tracking, no workflow trigger
"How's Sprint 14 doing?" / "What releases are waiting on approval?"Reads burn-down/status, or lists issues by label — no issue number needed

See How To for the underlying workflows this drives, field by field, or the full skill reference for the exact recipes and confirmation rules.

Example: filing a bug and a task, step by step

Illustrative walkthrough against acme/storefront, a repo with Delivery OS installed (same example repo as the full walkthrough below).

Filing the bug:

  1. In Claude Code, inside (or pointed at, via --repo) the target repo, describe the bug in plain language:
    "File a bug on acme/storefront — the order request form submits with an empty phone number, severity high. Steps: fill in the form, leave phone blank, submit. Expected: should block submission. Actual: submits anyway, so there's no way to contact the customer. Tested on Chrome, desktop, production."
  2. Claude pre-flights the repo — confirms Delivery OS is installed and the bug/qa labels exist.
  3. Claude shows the exact issue it's about to create before doing anything: Title [BUG] Order request form submits with empty phone number; Labels bug, qa; body fields (Platform, Severity: High, Build/Version, Steps to Reproduce, Expected/Actual Result, Test Environment) filled in from what you said.
  4. Confirm ("yes") when asked to create it.
  5. Claude runs gh issue create and reports back the issue — e.g. acme/storefront#42. Nothing else happens automatically; bug reports don't trigger a workflow, they're just labeled and tracked.

Filing the follow-up task:

  1. Ask Claude to turn the bug into tracked work, referencing the bug's issue number:
    "Create a task to add phone number validation to the order form, owner @alex, priority P1, status Backlog, acceptance: form blocks submission until a valid phone number is entered. Link it to #42."
  2. Claude shows the constructed issue: Title TASK - Add phone number validation to order form; Labels task; body: Task Summary, Description (references #42), Owner → @alex, Priority → P1 - High, Status → Backlog, Acceptance Criteria, Artifacts/Links → Related bug: #42.
  3. Confirm ("yes") to create it.
  4. Claude runs gh issue create. Same as the bug — no workflow trigger, just labeled and tracked, now linked back to the bug it addresses.
Full example: shipping a feature end-to-end

A realistic Claude Code session, run from inside the consumer repo (the skill defaults to it since it was installed with --with-skill there). RELEASE_APPROVER, QA_APPROVER, and QA_ASSIGNEES are already configured.

You: Create a sprint called "Sprint 14 - Checkout Revamp", running 2026-09-16 to
     2026-09-30, goal is shipping the new checkout flow, features:
     - Redesign cart summary
     - Add saved payment methods
     - Fix tax rounding bug

Claude: This will create an issue in acme/storefront:

          Title:  SPRINT - Sprint 14 - Checkout Revamp
          Labels: sprint, planning
          Body:
            ### Sprint Name
            Sprint 14 - Checkout Revamp
            ### Sprint Start
            2026-09-16
            ### Sprint End
            2026-09-30
            ### Sprint Goal
            Ship the new checkout flow
            ### Sprint Features (One Per Line)
            Redesign cart summary
            Add saved payment methods
            Fix tax rounding bug
            ### Sprint Approved
            Pending

        Create this issue?

You: yes

Claude: Created #52. sprint-child-creator will fire on open and create one child
        issue per feature — #53 "Redesign cart summary", #54 "Add saved payment
        methods", #55 "Fix tax rounding bug" — each labeled sprint-active and
        linked back with "Parent Sprint: #52".

  [ ... engineers do the work, close #53 and #54 as they land ... ]

You: How's Sprint 14 doing?

Claude: Reading #52... ## 🚦 Sprint Status: 67% complete (2/3 closed), 20% of
        sprint time elapsed, 🟢 on track.

You: QA found a rounding issue in the tax calc — file a bug. Severity high,
     repros on checkout with 3+ items, expected total matches line items,
     actual is off by $0.01.

Claude: This will create an issue in acme/storefront:

          Title:  [BUG] Tax rounding off by $0.01 with 3+ items
          Labels: bug, qa
          Body: (Platform, Severity: High, Steps to Reproduce, Expected vs.
                 Actual Result, Test Environment filled in from what you said)

        Create this issue?

You: yes

Claude: Created #56.

  [ ... #55 fixed, referencing #56 ... ]

You: Open a QA request for the tax rounding fix, related to #55, test on
     staging, acceptance: totals match to the cent for carts of 1-10 items.

Claude: This will create an issue in acme/storefront:

          Title:  QA REQUEST - Tax rounding fix
          Labels: qa-request
          Body: (Related Sprint Task Issue #55, What to Test, Environment +
                 Build Link: staging, Acceptance Criteria filled in)

        Create this issue?

You: yes

Claude: Created #57. auto-assign-qa will assign it to the configured
        QA_ASSIGNEES.

  [ ... QA tests it, comes back clean ... ]

You: Mark QA #57 as approved, looks good.

Claude: Checking gh auth status... authenticated as jane-qa, which matches this
        repo's QA_APPROVER. Posting:

          "looks good — verified on staging, totals match to the cent"

        on #57.

You: yes, post it

Claude: Posted. Now close #55 to update the sprint burn-down?

You: yes

Claude: Closed #55. Sprint 14 is now 100% complete — auto-close-sprint closed
        #52 and posted a completion comment.

You: Open a production release for storefront v2.4.1, sprint #52, summary
     "checkout revamp: new cart summary, saved payment methods, tax rounding
     fix", QA evidence: #57.

Claude: This will create an issue in acme/storefront:

          Title:  PRODUCTION RELEASE - storefront - v2.4.1
          Labels: release, production, approval
          Body:
            ### Sprint Reference (Sprint Planning Issue #)
            #52
            ### Version / Build Number
            v2.4.1
            ### Release Summary
            Checkout revamp: new cart summary, saved payment methods, tax
            rounding fix
            ### QA Summary + Evidence Links
            #57
            ### Overall QA Recommendation
            Approve for Production
            ### Deployment Authorized
            No

        Create this issue?

You: yes

Claude: Created #58. notify-release-approver posted a comment tagging this
        repo's RELEASE_APPROVER (john-lead).

  [ ... some time later, as john-lead ... ]

You: Approve release #58.

Claude: Checking gh auth status... authenticated as john-lead, which matches
        RELEASE_APPROVER. Posting "approved" on #58.

You: yes

Claude: Posted. authorize-deployment will add ready-for-deploy once both
        approvers (release + QA) have a qualifying comment on record.

Each "yes" above is a real confirmation gate — Claude shows the exact issue/comment content before it creates or posts anything, since it's a visible action in the repo.
